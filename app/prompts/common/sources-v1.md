# 信息源手册（采集 agent 共用）

本页讲**怎么用 Owli 的信息源工具**。每个采集章都会附上这一页，后面跟一张按
当前注册表生成的逐源表。加新源时改各源自己的 `SOURCE_SPEC`，逐源表会自动更新；
本页只写对所有源都成立的规矩。

## 1. 证据只能来自源工具的返回值

- 产物里每一条记录的 `permalink`，**必须是本章那个 `source.*` 工具这次返回过的**。
- 引擎自带的联网搜索（如果你有）**只能用来想查询式**，它的结果不得写进产物、
  不得当证据。原因不是洁癖：源工具的返回会**直接入库**，自带搜索的结果只落在
  产物文件里，一旦本章超时，那批数据会连同产物一起作废——等于白搜。
- 源工具取不到就如实记缺口（见第 4 条），**不许用自带搜索补位**。

## 2. 参数怎么填

- `query`：检索关键词。**一次一个主体、一个意图**。把四个产品名和五个话题
  用 OR 拼成一长串，多数源会命中率暴跌——宁可多调几次。
- `window`：时间窗，写成「天数 + d」，如 `7d` / `30d` / `90d` / `365d`。
  也接受 `最近一年`、`近三个月`、`不限` / `all` 这类人话，系统会折算。
  **有的源没有这个参数**（工具 schema 里就不会出现它），那说明该源的检索
  本身不支持时间窗，别自己想办法补。
- 条数：由本章任务里的 `limit=` / `max_results=` 给定，那是**本档位的名额**。
  不要自行调大，也不要因为「怕不够」而反复重搜同一个词。

## 3. 一次调用取不到，怎么办

- **先换查询式，别换工具。** 关键词拆细、去掉 OR、换同义词，通常比重试有用。
- 工具返回了明确的失败原因（`closed_reason`），照它办：
  - `tikhub_http_429` —— 打太快了，慢一点、少调几次，不要立刻重试同一个词。
  - `tikhub_auth` —— 凭证问题，**你解决不了**，如实记缺口，不要绕道。
  - `tikhub_http_5xx` / `tikhub_transport` —— 供应商或网络抖动，可以隔一会儿
    再试**一次**；连续失败就记缺口收工，别把本章的时间耗在重试上。
  - `tikhub_bad_response` / `tikhub_upstream_code` —— 上游返回不对劲，
    换查询式再试一次，仍不行就记缺口。
- **重试是有预算的**：本章有墙钟，反复重试的代价是整章超时、所有已采数据作废。
  取到一半也比整章作废强——先把已经拿到的写进产物。

## 4. 取不到就如实说

- 缺口按结构化口径写：查询词、命中数、原因，一条不落。
- 不要用「搜索摘要」冒充原文，不要凭记忆补数据，不要编 `permalink`。
- 少采到不丢人，**假装采到了**才是事故。
